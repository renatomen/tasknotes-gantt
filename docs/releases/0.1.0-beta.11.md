# TaskNotes Gantt 0.1.0-beta.11

The largest release so far, and the first since July: working-time calendars arrive as a complete feature — calendar notes, a visual editor, working patterns, availability, and calendar sets — alongside a context-aware legend, independent bar treatment channels, and TaskNotes calendar items rendered directly in the timeline. It also carries an important date-handling fix for anyone in a timezone behind UTC.

## Added

- **Calendars and working time.** (#267, #268, #269, #270, #271, #272, #273, #275, #276, #277, #278, #279, #281)
  - The Gantt now understands *when work actually happens*. A calendar is an ordinary note in your vault describing a working pattern, and once you select it, non-working days are drawn as background shading instead of passing for ordinary workdays. Scheduling is at **day granularity** for now: you can author working hours and the editor's Week preview shows them, but nothing schedules or shades by them yet — two calendars differing only in their hours produce the same chart.
  - Set **Estimate meaning** to *Working days* and a task with one real date whose other end the plugin worked out for you — from a time estimate, or from the default task duration when there is no estimate — stretches across those blocked days rather than running through them. This is opt-in: the setting ships as *Calendar days*, which leaves those spans flat. Dates you authored yourself never move, and a task with no dates at all keeps its placeholder bar as-is. Note that stretching follows the calendar **the task itself points at**, through its Calendar Property — selecting a calendar shades the chart, but a task with no calendar of its own never stretches.
  - Calendars combine into **calendar sets**, so a team calendar, a personal one, and a holiday calendar can apply together — each member is a wikilink to another calendar note in your vault. Where two calendars disagree, the chart surfaces the conflict rather than silently picking one, and a status banner tells you when a calendar **you selected for display** could not be resolved. One caveat worth knowing: a broken link in a *task's* own Calendar Property is not reported there — that task quietly schedules as though it had no calendar.
  - Pick calendars with the **Select calendars…** command and its picker modal, see a calendar's markers and a today line over the timeline, and optionally use the calendar as a bar colour source so each task carries the colour of the calendar it belongs to. An **Open calendar note as markdown** command drops back to the raw note whenever you want it.
  - Working patterns are written as standard iCalendar recurrence rules (RFC 5545 `RRULE` values), so the syntax is the one you already know from any calendar tool and says the same thing here. The note itself is still plugin frontmatter — there is no `.ics` import or export yet.
- **A visual editor for calendar notes.** (#286, #287, #288, #289, #290, #291, #292, #293, #294, #295, #296, #297, #298, #300, #301, #303, #304, #305, #306, #307)
  - Open a calendar note and edit it as a form instead of by hand: a working-pattern builder for the recurrence rules, a searchable timezone picker showing live UTC offsets, and a collapsible colour picker accepting CSS colour names or hex.
  - Three preview tabs show the pattern you are building before you commit to it — a **year grid**, a **week** view, and a **Gantt strip** — and conflicts between calendars in a set are explained on hover.
  - The editor keeps a sticky header with its tabs, Save button, and an unsaved-changes cue, and warns before you close a note with unsaved edits. Comments in your note's frontmatter survive a save, except inside a field you actually changed — rewriting a list replaces the whole block, comments included.
  - New **Create calendar** and **Create calendar set** commands start a note from a template, and a calendar can be renamed from a Name field in the editor.
- **Availability blocks — extra working time beyond the main pattern.** (#308, #321)
  - A calendar can carry availability blocks alongside its top-level pattern, each with its own recurrence. They are **added** to the working days, not subtracted from them: a Mon–Fri pattern plus a Saturday availability block works Mon–Sat. Use them for a recurring on-call rotation, a Saturday shift, or a second working window the main pattern does not describe.
  - Days off go the other way, in the calendar note's `non_working` list — that is where a holiday, a training day, or a week away belongs.
- **TaskNotes calendar items in the timeline.** (#386)
  - The Gantt can render what the TaskNotes calendar shows: recurring task instances, time entries, timeblocks, property-based events, and external calendars (ICS, Google, Microsoft). A recurring task renders as one authored row whose bar carries a piece for each occurrence, and falls back to a single series spine at zoom levels too coarse to tile those pieces honestly.
  - Every family ships **off** — the chart stays a pure task timeline until you opt one in. The exception is recorded recurring occupancy (completed, skipped, or materialized instances), which stays visible because that is what the TaskNotes calendar itself contributes.
  - Per-view toggles mirror the TaskNotes calendar's own, and a source switcher hides or restores any contributing source for the current opening without changing your saved settings. External calendars are read entirely through TaskNotes' own subscription services — the Gantt adds no feed, credential, or fetch of its own, and the background check that notices a feed changed never touches the network. Displaying a visible ICS feed does go through TaskNotes' service, which fetches when its cache is cold or expired, so opening such a view can still cause network activity on TaskNotes' behalf. Calendar items are read-only — your task bars stay the single editable representation of a task's dates.
- **A context-aware interactive legend.** (#391, #406)
  - Every chart can now explain itself. The legend samples the view you are actually looking at — its theme, palettes, treatment choices, calendar colour, estimate meaning, and non-working-time rendering — and covers task, date, calendar, dependency, occurrence, estimate, and per-task override semantics.
  - It overlays the chart at the right or bottom and can be moved live for the current opening; the Appearance setting chooses the default position for future openings. The chart stays mounted throughout, so geometry and selection survive opening, moving, and closing it.
- **Hovering a dependency arrow describes the dependency.** (#404)
  - Point at the connector itself and the tooltip names the relationship it represents, rather than leaving you to trace the arrow between two rows. Hovering a task lists every dependency coming into it.
- **Independent Bar fill, Bar strip, and Task icon channels.** (#312)
  - **Bar fill** and **Bar strip** are now chosen separately. A single colour source plus a fill-or-strip mode used to drive both together, so you could have one or the other but never a different source for each; now you can fill by status while striping by priority. **Task icon** was already independent and stays so.
- **Estimate meaning is its own setting, separate from how non-working days are drawn.** (#315, #319, #320)
  - Two questions that used to share one control are now separate. **Estimate meaning** decides whether a worked-out duration means working time (re-projected across working days) or elapsed calendar time. **Non-working-day rendering** decides whether blocked days are shown only as background shading, or also as dimmed segments inside the bar — *Split segments* adds the segments, it does not replace the shading. A bar whose whole span is blocked has nothing to divide and stays continuous. Every combination is now reachable, including elapsed-time dates with the non-working days still drawn in.
  - Estimate meaning has a per-view default and a **per-task override** property. An overridden task carries a small accent dot on its upper-left corner, with a halo so it stays visible over any bar colour, and hovering it explains the interpretation — on tasks that resolve to a calendar. Without one the span cannot re-project, so the bar stays flat and carries no dot, since a marker there would advertise a difference the bar does not show.
  - Authored dates are never moved by either setting — only the ends the plugin worked out for you re-project.
- **A prompt when you drag a task whose dates are inferred.** (#314, #336, #347, #348)
  - Resizing the worked-out end of a bar — the end you did not author — now asks what you meant. Both answers update the time estimate to match the span you dragged, up or down. The exception is narrow: when a task already stores an estimate working out to the same day count, that write is skipped — though **Estimate and dates** still pins the date. A task storing no estimate always gets one written. **Estimate only** leaves that edge computed, while **Estimate and dates** additionally pins a real date on the edge you dragged, leaving the end you authored untouched. The answer applies immediately, and a **Don't ask again** toggle saves it as this view's *Inferred date drag* setting so future drags skip the prompt; set that option back to *Ask* in view options whenever you want the question again.
  - The question only arises where growing the estimate is actually possible, so it needs **Time Estimate Update** set to write somewhere. That setting ships as *Don't update*, and in a view left that way an inferred-edge resize simply writes the date, as before. Moving a whole bar, and dragging a task that has no dates at all, never prompt either.
- **A torn edge marks a date the task does not actually have.** (#395, #397, #398, #406)
  - When one end of a bar is inferred rather than written down, that end is cut with a zigzag edge instead of a flat one, so an inferred boundary never looks authored. A task with neither date is torn at both ends. The tear now carries the meaning by itself — there is no accompanying fill or border colour for it — and the legend explains it.
  - One limit worth knowing: a bar too narrow to carry a tooth — a one-day task at the coarsest zoom levels, and sometimes a narrow split piece — shows no date-status cue at all.

## Changed

- **Leaving the status, priority or date mappings blank now means "use the TaskNotes default", not "no property".** (#254)
  - A blank *Status Property* previously switched off everything that depended on status: colouring bars by status did nothing, the status icon did nothing, and double-clicking a status cell opened the note instead of the picker. Blank mappings now resolve to the properties TaskNotes is configured with, for status and priority as well as dates, and inline editors resolve against the same values.

## Removed

- **The red border on tasks with swapped dates.** (#412)
  - A task whose start falls after its due date no longer draws a red outline. The orange fill still marks it. A fuller treatment — a badge beside the bar naming what is wrong — is planned; until it ships, a swapped task shown with split rendering carries no visible cue.

## Fixed

- **Tasks no longer shift by a day when you edit their dates.** (#311, #489, #490)
  - Dates written as plain calendar days were read as UTC instants, so in any timezone behind UTC a task saved as September 21–23 drew on September 20–22 — and dragging it then saved the wrong day, compounding with every correction. Calendar dates are now read as calendar dates.
  - Three further defects found while verifying that fix are also closed: a moved three-day bar could briefly display as two days, closely spaced corrective moves could roll back after a refresh, and resizing a task that appears in more than one place could leave the other copy behind.
  - One symptom from the original report — an intermittent change in bar width during a drag — was not reproduced, so #311 stays open for it. Please keep the reports coming if you still see it.
  - Thanks to @donaldwdci for reporting this and for the detailed follow-up that made the remaining causes findable.
- **Tooltips never appeared on touch-capable hardware, and dependency tooltips were empty everywhere.** (#404)
  - Any device reporting a touch point — including most laptops with a touchscreen — suppressed every tooltip in the chart. Tooltips now appear on anything that can hover, a touchscreen laptop included; a touch-only device still has none, since a tooltip is a hover affordance.
  - Separately, and on every device: the chart hands tooltip content a wrapper around whatever was hovered, and the plugin read it as though it were the task, so dependency tooltips rendered as an empty box. They now carry their content.
- **Two Gantt views in one workspace no longer interfere with each other.** (#316)
  - Injected styles were shared across views, so opening a second chart could restyle the first. Each chart now owns its own.
- **Rows now appear and disappear when their dates change, instead of at the next reopen.** (#472, #473)
  - With *Show date-status indicators on bars* off, filling in a date a task was missing left *Show tasks with no dates* and *Show tasks with only one date* filtering that row on the classification it used to have — so a task you had just given real dates could stay hidden, and the toolbar could read "6 results" over a four-row chart, until you reopened the view.
  - *Hide top-level subtasks* removes the duplicate top-level copy of a task that also appears as someone's subtask. A task that became a subtask during a refresh kept that duplicate on screen anyway.
- **Icons on one-cell bars are aligned.** (#393)
- **A live Bar fill change no longer garbles split rendering.** (#318)
- **The legend's swatches match the chart.** (#402, #407, #410)
  - The torn-edge swatch now shows the same cut the chart draws, shading swatches have cells to contrast against, and the legend no longer describes a treatment that was retired.
- **Calendar editing and validation.** (#299, #302, #323, #324, #326, #327, #328, #329, #330, #331, #333, #334, #335, #337, #338)
  - Impossible dates are rejected, as are recurrence rules a day-granularity calendar cannot evaluate safely — malformed ones, and ones whose occurrences would drift with whichever window you happen to be looking at — before either can freeze or mis-render the preview. An ordinary open-ended rule, such as a plain Mon–Fri weekly pattern, is still accepted as always.
  - A colour is sanitised before it reaches an inline style; Discard is disabled while a save is in flight; a newly created calendar note routes to the editor even when the vault indexes it late; deleting a calendar note re-resolves the chart; folder-qualified calendar links resolve; and the conflict banner attributes each conflict to the calendar it came from.
